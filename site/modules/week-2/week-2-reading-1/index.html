A Family Logistics Coordinator

Learning objectives: Explain how instructions, current context, memory, tools, and orchestration shape an agent’s behavior.; Design a useful multi-step workflow with relevant information, narrow capabilities, checks, and stop conditions.; Match permissions and human review to an action’s impact, reversibility, uncertainty, privacy, and affected people.; Evaluate an agent’s result against evidence and the original goal, then choose to accept, revise, retry, or stop.

Content

A family logistics coordinator, designed one boundary at a time

Purpose: Show how the parts of an agent harness fit together in a multi-step task. Reading time: 6–8 minutes Objectives: LO2, LO3, LO4, LO5

A family has a weekend tournament in another town. Someone needs to check the schedule, estimate when to leave, find a nearby place for lunch, and prepare a message for relatives. It is a real coordination problem: multiple sources, a sequence of steps, and several people affected. It is also a useful place to practice designing an agent before handing it authority.

Start with a goal and a finish line

“Handle the tournament weekend” is too broad. A bounded goal could be: “Prepare a draft itinerary using the schedule I provide and public map information. Flag uncertainties. Do not book, pay, or message anyone.” The finish line is an itinerary ready for a parent to review, not an automatically completed weekend.

The instructions now identify the requested output, the allowed sources, and the actions that are off limits. They also say what should happen when the information is unclear: flag it, rather than fill in the blank with a guess.

Give each step the right context

The agent may need the venue address, game times, estimated driving time, and the family’s chosen lunch window. It probably does not need the child’s full school record or access to all family messages. If the schedule is an image or PDF, the agent should show the extracted times so the parent can confirm them. If a map estimate omits parking or event traffic, the itinerary should say so.

Current task context and saved memory play different roles. A current instruction might specify, “We need a 20-minute buffer this Saturday.” A saved preference might say the family usually prefers vegetarian food. Both can be useful, but a remembered preference should be visible and changeable. If the trip is unusual, ask rather than assume the preference applies.

Sequence the work

A reasonable workflow is: read the provided event schedule; confirm the dates and venue; retrieve a travel estimate; identify a few lunch options; draft a timeline; list assumptions and missing information. The agent can check the result against the original schedule before returning it.

Notice how each step has a source and an output. The travel estimate comes from a map service, but the event times come from the schedule. The restaurant list is a set of suggestions, not a reservation. If a source is inaccessible, the agent can report that instead of quietly substituting an unknown source.

Treat memory and tools carefully

A map connection may expose a location. A restaurant service may show recent searches. A messaging tool may be able to contact relatives. These are separate capabilities. A workflow that only prepares an itinerary has no reason to send messages or make reservations. Least privilege means granting only what the current task needs, then removing access when it is no longer needed.

The agent could draft a message that says when the family expects to arrive. A parent should check the time and recipients before sending. If the itinerary includes a child’s location or schedule, sharing it has privacy implications. Ask who needs the information and how much detail is appropriate.

Check what “done” means

A formatted itinerary is not evidence that every detail is correct. Compare the games against the source schedule. Check travel estimates against the real event location and current conditions. Confirm that the lunch option is open and meets any dietary needs. Then decide which parts to use. If a source is missing or conflicting, keep the uncertainty visible.

The same design pattern works for a school open house, a family visit, or a volunteer event. Describe the task narrowly, give relevant context, sequence steps that can be checked, and stop before the workflow makes commitments. As experience grows, a family may choose to automate a low-impact step, but it should do so deliberately.

An agent harness is not a technical mystery. It is the practical arrangement of instructions, information, memory, tools, and stop rules. Making those pieces visible helps a family decide whether the system is ready for a task—and which parts still belong to a person.
