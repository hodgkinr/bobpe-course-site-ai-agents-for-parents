Video 3: The harness around the model

Duration: approximately 10 minutes Objectives: LO2, LO3 Purpose: Explain how instructions, context, memory, and tools shape an agent.

A model is only one part of an agent system. The harness sets the task, supplies relevant information, exposes tools, and records or retrieves context. Instructions express goals and boundaries; context gives the system the details it needs now; memory stores information for later use; tools create capabilities. Each part can improve usefulness and introduce risk.

Using a family meal-planning scenario, the lecture separates current-task context from persistent memory and shows how a small, explicit set of preferences can be safer than broad personal history. Learners consider how to make instructions observable and how to handle missing or conflicting information.

Lecture script

Video 3 script — The harness around the model

[Opening: a simple model icon surrounded by cards labeled instructions, context, memory, and tools.]

Last week we used a loop to describe an agent: receive a goal, propose a step, use a tool, inspect the result, and continue or stop. Today we will look at what surrounds the language model and shapes that loop. People sometimes call this the agent harness. The harness is the collection of instructions, information, tools, and software that makes a model operate as part of a larger system.

A useful analogy is a family road trip. The model is a driver who can reason about the next turn, but it only knows the destination and the road conditions that the system provides. Instructions are the trip rules: keep to the planned route, stop for breaks, and ask before taking a toll road. Context is the information for this trip: the destination, the current location, and a notice that one road is closed. Memory might be a saved preference, such as avoiding long drives after dinner. Tools are the map, car controls, and booking services.

The analogy has limits, because a model can misunderstand and a software system can supply incomplete information. That is exactly why each part deserves attention.

First, instructions. A request like “help organize our week” is broad. A more useful instruction might say, “Create a draft schedule from the events I provide. Preserve school commitments. Show conflicts, and ask before sending invitations or moving an event.” Good instructions name the task, the boundary, and what to do when things are unclear. They cannot guarantee that the system will follow every rule, so important boundaries should also be enforced by the software permissions.

Second, context. This is the information supplied for the current task. For meal planning, it might include the number of dinners, a list of ingredients, and a dietary constraint. Context should be sufficient, relevant, and current. If you include a huge archive of messages and notes, the important detail may be harder to find and private information may travel farther than necessary. A short, task-specific brief is often better.

Third, memory. A system may save a preference between conversations: “We prefer vegetarian dinners on Mondays.” That can reduce repeated explanation. But a remembered detail may be wrong, outdated, or about another person. Treat memory as a convenience that needs controls: Can you see it? Correct it? Delete it? Does the agent ask before saving sensitive information? Do not assume that a product’s use of the word memory means the same thing in every setting.

Fourth, tools. An agent may have access to search, a calendar, a recipe collection, or a shopping service. The harness determines whether it can read information, create a draft, change a record, or complete a purchase. Instructions can say “ask before buying,” but if the system already has payment authority, a mistaken step may happen quickly. The safer design is to withhold payment permission until it is genuinely needed.

[On screen: Task → Instructions + Relevant context + Narrow tools → Proposed steps → Check.]

Let’s design a meal-planning helper. The goal is to suggest four dinners. The minimum context includes the number of people, time available, and food constraints that matter. The system might use a recipe search tool, but it does not need access to a family’s private messages. It can produce a shopping list. The parent checks ingredients and labels, especially where allergies or medical needs are involved. If it can add products to a cart, that is a separate capability, and purchasing stays with a person.

Now consider an important edge case: the agent finds conflicting information. One saved note says a child dislikes nuts; a recent request asks for a recipe with peanut sauce. A weak workflow guesses. A better workflow flags the conflict and asks. The instruction “if information conflicts, pause and ask” gives the system a safe next move. The surrounding interface should also make it possible to stop the process.

A harness can be thoughtfully designed and still fail. Maybe the preference was saved incorrectly. Maybe the recipe page is old. Maybe the tool result leaves out an ingredient. A final check asks whether the output satisfies the goal and uses trustworthy evidence. We do not evaluate the system by how confident or polished it sounds. We compare what it did with the instruction, the source information, and the real-world need.

Here is a practical audit for any agent you are considering: What did I ask it to do? What information can it see? What can it remember? Which tools can it use? What actions are blocked or require approval? What will it do when uncertain? Can I inspect and correct the result?

These questions turn a vague product promise into a design you can reason about. The model matters, but the harness determines much of the real-world behavior. In our next lecture, we will coordinate several steps into a workflow and decide where the process should stop.

It is useful to pause on the difference between instructions and controls. Instructions tell the model what outcome you want and how you expect it to behave. Controls determine which actions the system can actually carry out. Suppose you tell a meal planner, “Never buy ingredients without my approval,” but then connect an account with one-click purchasing and no approval screen. The instruction is helpful, but it is not a strong boundary by itself. For consequential actions, combine clear instructions with technical limits where the service supports them.

Context deserves the same care. Imagine asking for a weekly meal plan and pasting a year of family messages to explain everyone’s preferences. The system may have more information than it needs, and old statements may no longer apply. A short brief—number of dinners, available time, foods to avoid, and budget range—can be easier to interpret and easier to review. If a preference is uncertain, state that uncertainty rather than hiding it inside a large archive.

Memory can also affect how an agent behaves without being visible in the current conversation. A useful family practice is to periodically inspect saved preferences, correct outdated information, and remove details that are no longer needed. Ask whether the system is saving something for future use, especially if that information involves a child or another family member.

When the agent reports a conflict, make the handoff specific. “I found two event times and cannot tell which is current. Here are the sources. Please confirm before I schedule anything.” This is better than a vague failure notice because it tells the person what is uncertain and what decision is needed. A good harness makes asking for help an expected path, not an embarrassment.

Finally, remember that the same model can behave differently in two products because their harnesses differ. One may have a narrow search tool and no memory. Another may connect to accounts and save preferences. Comparing models alone misses the instructions, retrieval, permissions, and interface that shape behavior. When choosing a service, inspect the whole arrangement around the model.

[Closing: A useful agent is shaped by the task, the information, the tools, and the boundaries around the model.]
