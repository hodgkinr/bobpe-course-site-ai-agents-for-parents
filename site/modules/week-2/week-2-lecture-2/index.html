Content

Video 4: Orchestration, stop rules, and handoffs

Duration: approximately 10 minutes Objectives: LO2, LO3, LO5 Purpose: Show how multi-step tasks are coordinated and how to prevent a workflow from continuing past its useful boundary.

Orchestration is the coordination of steps, tools, and sometimes specialized agents. A workflow may run in a fixed sequence, branch when information differs, or repeat a step until a condition is met. Every loop needs a purpose and a stopping condition. Without clear limits, systems may repeat searches, act on weak assumptions, or make unnecessary changes.

The lecture uses a family trip-planning task to introduce checkpoints, handoffs, fallback paths, and bounded retries. Learners consider how to divide the work, when a specialist tool is appropriate, and how a human can intervene if a source is unavailable or a conflict appears.

Lecture script

Video 4 script — Orchestration, stop rules, and handoffs

[Opening: a map with several stops and a visible “review here” marker.]

An agent can be asked to do more than one thing. It might gather information, compare choices, prepare a plan, and ask for approval. The coordination of those steps is called orchestration. You do not need to build software to reason about it. You already orchestrate tasks when you decide what must happen first, what can happen in parallel, and where another person should check your work.

Let’s return to the tournament weekend. The family wants an itinerary. First, the agent reads the event schedule. Next, it checks travel times. Then it finds lunch options and drafts a timeline. Finally, it reports assumptions and asks the parent to review. That is a simple sequence: the travel and lunch steps depend on knowing the venue and schedule.

Some steps can happen at the same time. Once the venue is known, the system could find parking information and lunch options in parallel. That may save time, but it also means there are two sources to check. More moving parts can make a workflow faster while making its results harder to inspect.

A workflow can also branch. If the event address is missing, the agent should ask for it or stop with a clear note. If the schedule lists two possible start times, it should show both rather than choose one. If a restaurant’s hours cannot be verified, it can label that option as uncertain. A branch is simply a rule that says what to do when the situation differs from the expected path.

[On screen: Read schedule → Check venue → (map estimate + lunch ideas) → Draft itinerary → Parent reviews.]

A useful workflow has a finish line. For the itinerary, that could be “return a draft with sources and unanswered questions.” Without a finish line, a system might keep searching for a perfect restaurant, repeatedly adjust a route, or make extra suggestions that do not help. A loop needs an explicit reason to continue, a maximum number of tries, and a condition that tells the system to stop.

This is especially important when an agent can use tools. Suppose it searches for a restaurant, cannot confirm availability, and keeps trying slightly different queries. That may be fine for a low-stakes lookup, up to a limit. It is not fine if the system then makes a reservation or sends messages to multiple places without asking. A retry rule should not silently expand authority.

Now imagine dividing the task among several specialized assistants: one extracts the schedule, one checks the route, and one suggests lunch. This can be called a multi-agent workflow, but “more agents” does not mean “more reliable.” Each handoff can lose context, duplicate work, or pass along an error. A person may need a short summary of what each step assumed and what evidence it used. For a simple trip plan, one system using a few tools may be clearer than a team of AI agents.

Handoffs need ownership. If a map tool cannot find the venue, should the system ask the parent? If the parent approves a draft, who is allowed to book? If a school policy is involved, who checks it? The workflow should say where the AI stops and who takes responsibility for the next step.

A small set of design questions helps. What is the first reliable input? Which step depends on it? Can two steps happen independently? What could go wrong at each handoff? What evidence comes back? How many retries are reasonable? Where should uncertainty cause the workflow to pause?

[Pause.] Think about a task with three or more steps. Draw arrows between them. Circle any step that changes a record, shares information, or commits money. Put a human review point before that action. Mark one condition that should make the system stop and ask.

Orchestration is not just a technical diagram. It is a way to make a process legible. If you can describe the goal, the sequence, the checks, and the stop rules, you can decide whether automation is useful and where a person should intervene.

In the final week, we will use these ideas to choose how much autonomy a task deserves. We will also plan what to do when the agent is wrong, because responsible use is not the belief that nothing will fail. It is designing for the possibility that it will.

Here is a small design exercise using a school open house. The input is the school’s event notice. The first step extracts the date, location, and session choices. A parent checks those details against the original notice. The next step looks up a route and estimates travel time. It then drafts a calendar event. The workflow ends at the draft. If the notice is unreadable or the route service returns two possible campuses, the agent stops and asks. This sequence is easy to explain because every step depends on information that came before it.

Now ask what could be parallelized. Once the address is confirmed, a route estimate and a list of nearby parking options can be gathered at the same time. But parallel steps need a combined review: are the parking details for the same campus, and are the sources current? Making a process faster can create more points where assumptions need to be reconciled.

A retry should change something for a reason. If the first search returns no current parking information, one revised search may help. Repeating the same search ten times is unlikely to create better evidence. A good rule might be: try one alternate official source, then mark the detail unconfirmed and let a person decide. This makes the stopping behavior predictable.

Multi-agent workflows add another layer. One helper might extract dates, another might research transportation, and a third might assemble a plan. If the date extractor misreads a notice, that error can travel to every later step. Each handoff needs enough source information for a person or later tool to check the claim. Specialized roles help only when they make the work clearer or more reliable than a simpler workflow.

The design question is not “Can the process run end to end?” It is “Can someone understand what happened, catch a meaningful mistake, and stop the system before its effects spread?” For an open house, an itinerary draft may be a good endpoint. For a task involving registration, payment, or child information, a person should review before the system proceeds.

[Closing: A workflow should know what to do next—and when to stop.]
